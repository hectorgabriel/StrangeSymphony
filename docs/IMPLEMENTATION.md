# Symphony .NET — implementation notes

This document records the behavior that [SPEC.md](../SPEC.md) leaves "implementation-defined", and the places where this port deliberately differs from it.

## Coding agent: Claude Code instead of the Codex app-server

The spec targets the Codex app-server protocol (§10). This port runs **Claude Code in headless stream-json mode** and keeps the same orchestration contract.

| Spec concept | This implementation |
|---|---|
| `codex` front-matter section | `claude` section. A `codex` key is ignored and logged as a warning. |
| `codex.command` (default `codex app-server`) | `claude.command` (default `claude`). It is launched as `bash -lc '<command> <flags>'` in the workspace, or with PowerShell on Windows. |
| App-server session over stdio | One long-lived `claude -p --input-format stream-json --output-format stream-json --verbose --session-id <uuid>` process per worker. |
| `thread_id` | The Claude `session_id`, generated by Symphony and passed with `--session-id`. |
| `turn_id` | The turn number within the worker (1, 2, …). `session_id` is `<thread_id>-<turn_id>`. |
| Turn start | One `{"type":"user",...}` line on stdin. |
| Turn completed / failed | A `result` message whose `subtype` is `success` (and `is_error` false), or an error subtype. |
| Continuation turns | Another user message on the **same process**. Only the continuation guidance is sent, never the original prompt again. |
| Session title | `--name "<identifier>: <title>"` |
| Tool advertisement | `--mcp-config <private file>` pointing to the host-side MCP gateway, plus `--allowedTools mcp__tracker`. |
| Token accounting | Each `result.usage` covers its own turn. Symphony sums them into absolute session totals (input = `input_tokens + cache_creation_input_tokens + cache_read_input_tokens`), and the orchestrator applies only the change since the last report. |
| Rate limits | The latest `rate_limit_event.rate_limit_info`, shown as `rate_limits` in the API. |

Other `claude` settings: `model`, `permission_mode` (default `acceptEdits`), `allowed_tools` (default `[]`), `disallowed_tools` (default `[AskUserQuestion]`), `extra_args`, `strict_mcp_config` (default `true`), `turn_timeout_ms` (3600000), `read_timeout_ms` (5000; reserved), `stall_timeout_ms` (300000, where `<= 0` turns it off).

The default `stall_timeout_ms` of 5 minutes can be too short for repositories whose builds or tests run long without printing anything. Raise it (the example uses 15 minutes).

## Authentication and accounts

Symphony **never reads, stores or forwards Claude credentials.** It runs the unmodified `claude` binary, which signs in the way that machine is signed in:

- **Per-member mode (recommended):** each team member runs their own Symphony, logged in with `claude` using their own Pro, Max or Team account, and sets `assigned_to: "@me"` with their own Azure DevOps PAT. Usage counts against that member's own plan, and tracker writes are attributed to that member.
- **API key mode:** set `ANTHROPIC_API_KEY` in the host environment. Use this for any shared or central deployment.

**Don't** collect several people's Claude logins on one shared Symphony host. See Anthropic's [legal and compliance page](https://code.claude.com/docs/en/legal-and-compliance) for the rules.

## Trust and safety posture (§10.5, §15)

| Area | Behavior |
|---|---|
| Intended environment | Trusted developer machines and VMs running against your own repositories. |
| Approvals | `--permission-mode acceptEdits` (file edits inside the workspace are auto-approved) plus `--permission-prompts none`. Any action that would need approval and isn't in `allowed_tools` is **denied automatically**. Nothing ever waits for a person. |
| User input | `AskUserQuestion` is disallowed by default. Approval requests are denied as above. A turn therefore can't stall waiting on input. If the agent gives up, the turn still ends with a `result`, and failures retry with backoff. |
| Shell access | Not granted by default. Grant narrowly, for example `Bash(git *)` or `Bash(dotnet test *)`. Use `bypassPermissions` only inside a disposable VM or container. |
| MCP isolation | `--strict-mcp-config` stops your personal MCP servers from loading into agent sessions. |
| Tracker credentials | Stay in the Symphony process. The agent gets a random bearer token for one session, valid only for this loopback gateway and only for the current work item. Adapter secret variables and `CLAUDECODE` are removed from the agent's environment. The MCP config file sits in the user's local app-data folder (`<LocalApplicationData>/symphony/mcp`) with mode `0600` on macOS and Linux, and the per-user ACL of `%LOCALAPPDATA%` on Windows (outside the workspace) and is deleted when the session ends. |
| Workspaces | Folder names keep only `[A-Za-z0-9._-]`. If cleaning changes a name, a 64-bit SHA-256 suffix is added; so do names Windows can't hold (device names such as `CON` or `COM1`, and a trailing dot), on every OS so keys match across machines. The path must sit inside the root, symlinked workspaces are rejected, and the agent's working directory is checked before launch. |
| Hooks | Fully trusted configuration. They run in the workspace through `bash -lc` (or the shell named by `hooks.shell`) with `hooks.timeout_ms`, and their output is cut to 8 KB in logs. |
| HTTP | The dashboard/API and the MCP gateway bind to `127.0.0.1` only. |

## Other implementation-defined choices

- **Existing non-directory at a workspace path:** creation fails, and the file is left alone.
- **`after_create` failure:** the partly created directory is removed. Reused workspaces are never reset.
- **Invalid `WORKFLOW.md` reload:** the last good config stays in effect for reconciliation, retries and running sessions. *New dispatches are paused* until the file is fixed (§5.5). The error shows in logs and in `workflow_error` in the API.
- **Workflow reload:** triggered by the file watcher and by a content-hash check before every tick. A successful reload starts an immediate tick.
- **Tracker reads off the loop:** tick and retry reads run in the background and their results come back to the orchestrator loop as messages, so a slow tracker never delays agent events, worker exits or `/api/v1/state`. One tick fetch runs at a time; refresh requests that arrive meanwhile coalesce into a single follow-up tick. A reconcile result only applies to the run it was fetched for, never to a newer run of the same issue.
- **Tracker adapter lifetime:** each reload builds a new adapter. Running workers keep the snapshot they started with, and a replaced adapter is disposed when the last worker using it exits.
- **Tracker rate limits:** when a tracker error carries a retry-after hint (Azure DevOps `Retry-After` on 429), the next scheduled poll and any failed retry refresh wait at least that long. A manual `/api/v1/refresh` still runs immediately.
- **Retry dispatch while the workflow is invalid:** the issue is requeued with the error `workflow invalid; dispatch blocked`.
- **Reconciliation stop:** the worker is cancelled. Its claim stays (marked `stopping`) until the process exits, so the same issue can't be dispatched twice into one workspace. Terminal issues have their workspace cleaned only after the worker exits.
- **Stalled sessions:** killed, then retried with failure backoff (`error = stalled: ...`).
- **Continuations without progress (`agent.max_fast_continuations`, default `3`):** the spec retries a clean worker exit after 1 s, which loops forever when an agent keeps ending its session without moving the issue. After that many back-to-back clean exits with the issue in the same state, later continuations wait `min(10000 * 2^(n - 1), agent.max_retry_backoff_ms)` instead, with `error = no state change after N sessions in <state>; backing off`. A state change resets the count. `attempt` stays `1`.
- **Prompt engine:** Scriban in Liquid mode with `StrictVariables`. Unknown variables, unknown members and unknown filters all fail rendering. Template syntax is checked when the workflow loads (`template_parse_error`).
- **Retry kind:** not exposed to templates. `attempt` is 1-based for both continuations and failure retries (§12.3).
- **Logging:** `key=value` lines on stdout through `Microsoft.Extensions.Logging` simple console, with UTC timestamps.
- **Snapshot API:** never blocks the scheduler loop. It reads the state published after each event. Before the first publish it returns `503 unavailable`.
- **Board (extension):** `/api/v1/state` adds `queue`, `last_poll` and `handoffs`. The dashboard shows them as a read-only board with five columns: Not eligible, Up next, Running, Retrying and Handed off. Cards link to the tracker, where tasks are changed. `queue` lists every candidate from the last successful poll, in dispatch order, with a `status` (`running`, `retrying`, `claimed`, `ready`, `waiting`, `blocked`, `held`, `missing_labels`, `invalid`) and a plain-language `reason`. Reasons are recomputed on every publish, so they follow runs and retries between polls. `last_poll` has `at`, the last poll `error` (the previous queue is kept) and `active_states`. Only issues in the active states are fetched, so an issue in any other state never appears. Adapters explain `dispatchable = false` in `Issue.HoldReason` ("Not assigned to @me", "Blocked by WR-1 (Analizado)"). `handoffs` holds the 20 most recent releases, newest first, with the state the issue left in and why (`Moved to "Analizado"`, `Reached terminal state "Done"`). It is in memory only, so a restart clears it. An issue released after the last poll is hidden from `queue` until the next poll. `/score` shows the same state as a musical score, one stave per running agent. The board switches to it on the Konami code or five quick clicks on its logo and remembers that in the browser's localStorage; the score's Board button switches back.
- **Hook shell (`hooks.shell`, extension):** `auto` (default), `bash`, `powershell`, `pwsh`, or an absolute path to a bash. `auto` is `bash -lc` everywhere, so one `WORKFLOW.md` works on macOS, Linux and Windows.
- **Pull requests (`pull_request`, extension):** adds a host-side `create_pull_request` tool next to the tracker's tools. It opens a pull request only after checking that the branch is committed and pushed and has no build output, and after `verify_command` succeeds on that commit. Tools may now set their own timeout (`AgentToolSpec.TimeoutMs`); the gateway default stays 60 s. See [pull-requests.md](pull-requests.md).
- **Windows:** tested, including the Real Integration Profile. What differs:
  - *Bash is Git Bash, found by path.* A bare `bash` on Windows is usually `System32\bash.exe`, the WSL launcher, which runs the script in a Linux VM with other paths and other git credentials. The lookup order is `CLAUDE_CODE_GIT_BASH_PATH` (as Claude Code uses it), the installation that owns `git.exe` on PATH, then `%ProgramFiles%\Git`; anything under the Windows folder is skipped. Inside an installation, `usr\bin\bash.exe` is preferred over the `bin\bash.exe` redirector. When `auto` finds no Git Bash it falls back to Windows PowerShell and logs `outcome=shell_fallback` once; `bash` fails instead.
  - *Hooks run from a temporary script file*, not `-c`. Given more than about 8 KB on its command line, Git Bash runs nothing and exits 0, so a long hook would "succeed" silently. (stdin isn't used either: a command in the hook that reads stdin would swallow the rest of the script.)
  - *The agent starts directly* when `claude.command` names an `.exe` (`claude`, `claude.exe`, or a full path). There is no shell in between to re-encode the stream-json pipe in the console code page or to re-quote arguments. Anything else (an npm `.cmd` shim, a command with arguments) runs through the hook shell; a command line too long for Git Bash fails with `agent_not_found` instead of starting nothing. A PowerShell `CommandNotFoundException` also maps to `agent_not_found`, like bash's exit 127.
  - *Paths:* Git Bash's own `pwd` shows its mounts (`%TEMP%` appears as `/tmp`); use `pwd -W` for the Windows form. In `WORKFLOW.md`, write Windows paths with forward slashes or in single quotes: inside double quotes YAML reads `\U…` as an escape.
  - *Files:* a UTF-8 byte order mark at the start of `WORKFLOW.md` is ignored. Workspace removal clears the read-only attribute git puts on its objects and retries briefly while a just-killed process lets go of its files. A watcher event that finds the file still locked by the editor retries the read before reporting `missing_workflow_file`.

## Conformance

The tests in `tests/Symphony.Tests` cover SPEC §17.1–17.7 and the HTTP extension. The Real Integration Profile (§17.8) runs the installed `claude` CLI through two turns and one host-side MCP tool call:

```bash
SYMPHONY_REAL_CLAUDE=1 dotnet test --filter RealIntegration
```

Without that variable, the test is reported as **skipped**.

Not implemented: the SSH worker extension (Appendix A), and keeping retry and session state across restarts (§18.2 TODOs).
